HTF — Function & UI/UX Walkthrough

How every server-side function works, and how the UI/UX shell drives the frontend · generated from the live codebase

Part 1 — How each function works

1. Request entry & auth src/worker/index.ts · auth.ts

  • The Worker's fetch handler wraps the whole HONO app once per isolate with getAuth(env, request) — Freebuff OIDC sessions when a client ID is configured, otherwise a loopback development user. No per-route auth code exists.
  • Public routes: GET /api/auth/status (mode + database/files presence) and GET /api/health. Everything under /api passes requireUser then requireDb.
  • Mounted routers: workspace (root), /bots, /strategies, /backtests, /connections, /portfolio, /market. app.onError returns a JSON 500; unknown /api/* paths 404, everything else falls through to env.ASSETS (the built SPA).
  • privateJson(c, body, status) stamps Cache-Control: private, no-store on every authenticated payload.

2. Workspace, seeding & fast-forward src/worker/routes/workspace.ts · seed.ts

  • ensureWorkspace creates the operator row on first call; seedWorkspace fills it with the demo fleet (insertDemoBots: five live-mode paused bots, launch equity points, demo venues) when the data set is empty; clearWorkspace backs the Settings reset, and POST /bots/demo replaces the fleet with those five without touching connections or backtests.
  • loadBots is the read path every list endpoint uses: it loads the fleet and calls advanceRunning, which fast-forwards up to 12 running bots per request so a paused page still shows fresh equity. The engine tick itself is advanceBot (below).
  • buildEquitySeries(bots, rows, windowStart, t) buckets equity history into the dashboard's chart points.
  • Endpoints: GET /me, PATCH /workspace (rename/prefs), POST /workspace/reset, DELETE /workspace/data, GET /overview (equity curve, stage totals, fleet counts, attention list, event feed), GET /search (command-palette results).

3. Bot creation — one function for launch, import, backtest and train src/worker/routes/bots.ts

POST /bots ─────────────┐ POST /bots/import ───────┼─► validateSpec ─► createBot ─► INSERT + logEvent('Launched…') intent: live ──────────┤ │ intent: backtest ──────┤ └─ (import only, dry-run first: ready/problem rows) intent: train ─────────┘ │ intent ≠ live ⇒ park as mode:'paper', status:'paused' then queueRunForBot ─► scheduleBacktest / runTraining
  • validateSpec(db, owner, body) — resolves the strategy (catalog key, or inline rules → the custom strategy); folds the singular symbol spelling into symbols; runs every symbol through normalizeSymbol (unknown symbols are named in the rejection — they never reach the synthetic feed); checks the timeframe against the strategy's list; sanitizes params (sanitizeParams, or parseRules for uploaded rules); clamps capital and risk; derives status/stage. Returns a typed spec or an error reason.
  • createBot(db, owner, body) — the single live-launch function. validate → INSERT INTO bots → logEvent launch line → reload. Single launch, bulk import, and the import dry-run all call it, so an uploaded config gets exactly the validation a hand-launched bot gets.
  • POST /bots/import — accepts { items, intent: 'live' | 'backtest' | 'train' } (max MAX_IMPORT). It validates every row first (the dialog's review screen), then creates each bot through createBot. Non-live intents park the row as paper/paused and call queueRunForBot, which reuses scheduleBacktest or runTraining (auto-sweep, slim payload) with the bot's stored params or rules. Returns { intent, launched, failed, runs: { queued, training, backtests, errors } }.
  • GET /bots fast-forwards then lists; GET /bots/:id fast-forwards one bot, its trades, positions, events.
  • PATCH /bots/:id — trading-settings edits (symbols/timeframe/risk/params/connection/mode) are refused with 409 bot_active while the bot is running (pause/ground first), re-normalize symbols with the same ingress filter, and write a bot_events row listing every changed field — config changes show up in the event stream.
  • POST /bots/:id/control — ground / resume / pause / start / stop, each logged as an event. POST /bots/:id/cashflow records a deposit or withdrawal (the input to portfolio reconciliation). DELETE /bots/:id removes the bot.
  • GET /bots/accuracy & GET /bots/:id/accuracy — score every bot (or one) with measureAccuracy over a fixed bar window; the fleet version feeds the Edge ranking tab.

4. The engine tick src/worker/engine.ts · broker.ts

  • advanceBot takes a per-bot mutex (advanceLocked) so concurrent reads can't double-fill a position. Each tick: pull bars for the bot's symbol/timeframe, evaluate the strategy's signal(ctx), size the order from riskPct, route it through the execution seam — PaperBroker fills against the simulated wallet, while a live bot resolves its venue connections in venues.ts into real adapters and fills on whichever venue quotes the best price — then persist trades, positions, cash/equity, and logEvent every fill and failure.
  • fail() converts engine errors into bot_events rows instead of crashing the read path; write() persists the bot's new state in one statement.

5. Backtest & training core src/worker/routes/backtests.ts · backtest.ts

  • backtestWindow(timeframe, from, to, clock) clamps any requested range to the platform's 5-year history bound (HISTORY_YEARS in market.ts) — user-entered custom dates are clamped here, not just the defaults.
  • runBacktest(input) simulates candle-by-candle with fees and slippage, producing equity curve, trades, drawdown and summary stats; toCandles() adapts stored/synthetic bars for the data the platform actually has.
  • scheduleBacktest(db, owner, spec) — resolves symbol/timeframe/params or rules, checks the simulation budget (simBudget), inserts a backtests row as queued. Used by POST /backtests and by bot import's backtest intent, so both paths share one scheduler.
  • runTraining(db, owner, spec) — the grid trainer. Catalog strategies sweep their own param schema (defaultSweep picks ≤ 2 numeric knobs from the strategy's min/max bounds); uploaded-rules strategies expose their thresholds as knobs (customKnobDefs → applyCustomKnobs), letting custom bots join the same training. Every combo runs on the train window, then on a held-out test window; results come back as { knobs, runs, bestIndex, summary } and a bot_events training line is logged.
  • Endpoints: GET /backtests, GET /backtests/:id, GET /backtests/:id/market (the candles used by the run — stored bars first, synthetic fallback), POST /backtests, POST /backtests/optimize (same trainer, exposed for the Training page), DELETE /backtests/:id.

6. Strategy catalog & uploaded rules src/worker/strategies.ts · routes/strategies.ts

  • Catalog strategies (DCA, EMA Momentum, Mean Reversion, Grid, Range Breakout, Market Making, + the custom strategy) each carry a param schema and a signal(ctx) function over bars.
  • parseRules(raw) validates an uploaded rules DSL — entry groups and exit groups (all/any logic), metrics rsi | ema | zscore | donchian-high/low | momentum with window + threshold, plus stop/target. rulesToParams stores it as bot params; applyCustomKnobs substitutes swept values during training.
  • measureAccuracy(strategyKey, params, bars, tfMs) replays signals over a window and scores how often the predicted direction materializes — the "market edge" number used by the Edge ranking and each bot's accuracy card.
  • sanitizeParams clamps any inbound params to the schema (bounds, types, defaults) so a bad upload can't poison the engine.
  • routes/strategies.ts serves the catalog, plus durable versioned uploads: POST /strategies/custom stores a new version row (rules are also kept on the bot itself), GET /strategies/custom/:id/versions lists the history, DELETE removes it.

7. Market data — normalization, screening, 5-year store src/worker/market.ts · marketstore.ts · routes/market.ts

  • normalizeSymbol(raw) folds operator dialect ("btcusdt", "Btc/Usd", trailing spaces) onto catalog entries; unknown symbols return null and are rejected at every ingress instead of minting a plausible fake series.
  • The feed itself is a deterministic seeded series (priceAt, barsBetween, capped at MAX_BARS = 6000) spanning HISTORY_YEARS = 5 — the same bound the backtester clamps to (historyStart(at)).
  • screenRow / screenPayload — initial payload filtering for bulk imports: dedupe, timestamp sanity, OHLC consistency, unknown-symbol and stale-row rejection, each row returned with a status + reason; upsertBars writes accepted rows idempotently.
  • barsForRun prefers stored history for a backtest/training window and falls back to the synthetic series only where the store has no coverage — so a backtest reports on the data the platform actually stored.
  • Endpoints: GET /market/history (stored-backed candles for charts), POST /market/import (bulk ingest through the screener), GET /market/stored (coverage summary).

8. Portfolio — two books that never mix src/worker/routes/portfolio.ts

  • One GET /portfolio builds both books from a single batch query: cash flows and P&L are partitioned by bot mode (b.mode = 'live' vs 'paper'), so paper metrics can never blend into real capital totals.
  • Money book: summary KPIs (starting capital, current equity, net/realized/unrealized P&L, fees), fleet equity curve, per-bot audit rows, open positions, transaction ledger (CSV-exportable), allocation & liquidity (invested vs idle cash, per-holding equity), funding & reconciliation.
  • Reconciliation identity: launch funding + net funding (deposits − withdrawals) + trading P&L = current equity — equity reconciles against real cash flows, not just P&L, with a "Reconciled ✓" badge.
  • Weekly funding vs P&L: ISO-week buckets of net funding and realized P&L (mergeWeekly), plus a daily net-funding bar chart and the raw flow log.
  • Live book only: the money book, KPIs, ledger and audit rows are live-routed bots; paper bots are reported by GET /portfolio/paper and shown under Training → Paper portfolio, never in these numbers.

9. Connections src/worker/routes/connections.ts

  • Exchange API credentials for bots to route through: GET list (secrets never returned), POST /demo (two demo venues for testing), POST /bulk (multi-row JSON upload), POST /, PATCH /:id, DELETE /:id (strips the venue from every bot's routing set), and POST /:id/test (read-only credential probe where the venue offers one).
  • Each connection carries an environment (sandbox / production). BSE is wired live through Upstox: it has no public retail order API, so the adapter signs orders through a broker API, prices them from the venue in production and from the reference feed in the orders-only sandbox.
  • Instrument master (src/worker/instruments.ts): BSE keys every derivative by expiry and strike, so hardcoding tickers cannot work. The adapter downloads the exchange's BOD instrument file (BSE.json.gz — public, no credentials), stores the BSE_FO futures and options in bse_contracts, and resolves a catalog ticker to a live contract: futures to the nearest expiry, options to the nearest strike (catalog strikes are app units, scaled by INR_PER_APP_UNIT to match rupee strikes) on the nearest expiry. Orders are rounded down to the contract's lot size, so a too-small bot fails with the lot and notional in the message instead of sending an invalid quantity.
  • GET /instruments/bse (cached contract count, sync time), POST /instruments/bse/refresh (re-download), GET /instruments/bse/resolve?symbol=SENSEX-FUT (the exact instrument_key, lot size and expiry an order would use). The cache is trusted for six hours and refreshed lazily on the next order after that; a venue outage keeps serving the last good copy.
  • Catalog contracts: SENSEX-FUT, BANKEX-FUT, SENSEX50-FUT, FOCIT-FUT and index options such as SENSEX-940-CE / SENSEX-900-PE (asset class Futures / Options). They trade on the synthetic feed for paper and backtests and route to real dated contracts when live.

10. Cross-cutting: events & schema src/worker/db.ts

  • ensureSchema applies idempotent migrations on boot (bots, trades, positions, events, cashflows, backtests, connections, strategies + versions, market bars).
  • logEvent(db, owner, botId, level, message) is the single funnel into bot_events: launches, config edits, ground/resume, fills, training summaries, failures. Every screen reads the same stream.
  • Row mappers (mapBot, mapTrade, mapEvent, mapBacktest, …) are the only place SQL rows become API shapes.

Part 2 — How the UI/UX shell interacts with the frontend

1. Shell & chrome src/app/components/Shell.tsx

  • Every authenticated page renders inside Shell: left sidebar (Dashboard, Bots, Strategies, Training, Portfolio, Connections — plus Settings in the footer), brand block, a Search button bound to ⌘/Ctrl K, and currency (USD/EUR/GBP/INR) + theme toggles.
  • CommandPalette queries GET /search and deep-links to bots/pages. prefs.ts persists currency and theme in localStorage; currency conversion happens centrally in lib/format.ts (money(), moneyExact(), …) so every figure on every page converts together.
  • Mobile: the sidebar collapses behind an "Open menu" button; route changes close it automatically.

2. Routing & the auth gate src/app/App.tsx

QueryClientProvider (staleTime 15 s, retry 1) └─ ToastProvider └─ Pageviews → PostHog pageview on every SPA navigation └─ Gate → useMe() 401 → <SignIn/> 503 → <SetupNeeded/> ok → Routes under <Shell/> / Dashboard /bots Bots (list · lifecycle board · edge ranking) /bots/:id BotDetail (uptime, event stream, panels) /strategies Strategies (catalog · uploads) /training Training (train & optimize · backtests · paper portfolio) /backtests → redirects to /training?tab=backtests /portfolio Portfolio (live money book) /connections Connections /settings Settings
  • Gate decides the whole app shell from one useMe() query; a 401 drops to the sign-in screen, a 503 (no D1 binding) to the setup screen — pages never handle auth themselves.

3. Data layer src/app/lib/api.ts

  • api<T>(path, init) — one fetch wrapper; non-2xx throws ApiError carrying status + server message, which dialogs and toasts surface verbatim.
  • React Query hooks are the only read path: useMe, useDashboard, useBots, useBot, usePortfolio, useBacktests, useBacktestDetail, useBacktestMarket, useStrategies, useCustomStrategies, useConnections, useSearch, useBotAccuracy, useBotEdge — each with a stable query key.
  • useApiMutation(fn, invalidateKeys, { onSuccess }) wraps every write: it runs the API call and invalidates exactly the owning keys (e.g. an import invalidates bots, dashboard, portfolio, search), so one mutation refreshes every screen that shows the data.
  • Typed action clients: launchBot, importBots(items, intent), controlBot (ground/resume/…), adjustFunding, patchBot, deleteBot, runBacktest, optimizeTraining, uploadCustomStrategy, createConnection/uploadConnections/addDemoConnections, fetchMarketHistory.

5. Dialogs — where the flows live src/app/components/form-dialogs/

  • LaunchWizard (launch.tsx) — multi-step launch: strategy → symbols & timeframe (market/forex/crypto/option pickers) → risk & params → review; posts to launchBot.
  • BotImportDialog (botimport.tsx) — the three-destination upload: paste or drop a JSON array (or a .json file), see per-row ready / problem validation with reasons, choose destination Live / Backtest / Train, then submit through importBots(rows, intent). The description adapts to the destination; on success it toasts the counts and navigates to where the result lives (Backtest → /training?tab=backtests, Train → /training). "Download sample" emits a valid starter payload.
  • BacktestDialog — New backtest (works for uploaded-rules bots too), UploadStrategyDialog — rules-DSL upload, ConnectionForm + BulkConnectionsDialog — single and multi API-key upload.

7. One end-to-end example: importing a bot for training

operator drops JSON ─► BotImportDialog parses → reviewImport() dry-run (ready/problem rows) → picks destination "Train" → importBots(rows, 'train') → POST /bots/import { intent: 'train' } validateSpec → createBot (same function as live launch) → row parked paper/paused queueRunForBot → runTraining (grid over the bot's knobs, train + hold-out windows) ← { launched: [...], runs.training: [{ bestTrain, bestTest, combos, swept }] } → toast "Imported 1 bot · trained 1" → navigate /training → Training page shows the sweep; Apply-to-bot PATCHes the baked params (logged as a bot_events config change)
Read path in one line: page → hook (react-query) → api() → Worker router → row mappers → privateJson. Write path: dialog → useApiMutation → typed client → route → shared core function → logEvent → key invalidation refreshes every owning screen.
